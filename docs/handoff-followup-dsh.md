# 军师 · 追加发话（followup）接入交接

> 给手机端脚本维护方（DSH）。这份文档自包含，按它改即可，不需要看别的资料。

## 一句话

在手机端常驻脚本里加一个轮询：**每 60–90 秒问一次云端"有没有该补发的会话"**，有就拿返回的话术发到对应微信会话。

---

## 接口

```
POST https://opzvvgixlfbfpdlsorbi.supabase.co/functions/v1/ima-proxy
Content-Type: application/json
```

### 三种调用

**1) 脚本启动时（上线，必调一次）**

```json
{ "mode": "followup", "api_key": "<账号 API Key>", "online": true }
```

**2) 运行中轮询（每 60–90 秒）**

```json
{ "mode": "followup", "api_key": "<账号 API Key>" }
```

**3) 脚本退出 / 用户暂停时（必调）**

```json
{ "mode": "followup", "api_key": "<账号 API Key>", "action": "stop" }
```

`"action": "start"` 与 `"online": true` 等价。

---

## 返回

```json
{
  "followup": [
    { "session_id": "uuid", "friend_name": "小美", "text": "刚路过那家店 想到你说的",
      "shape": "半句钩子", "waited_min": 7, "used_today": 1 }
  ],
  "skipped": [],
  "offline": false,
  "disabled": false,
  "window": "09:00-23:00",
  "session_cap": 3,
  "online": true
}
```

- `followup` 为空数组 = 这轮没事，正常。
- `text` 是最终话术，**原样发出，不要改写、不要加标点、不要补称呼**。
- 用 `friend_name` 定位微信会话（跟你们主链路发消息用的是同一个会话映射）。
- `session_id` 只在排障时用，正常发送不需要。
- `used_today` 是该会话今天已补次数，仅用于日志。

---

## 停止语义（本次改动的重点）

- 调过 `action=stop` 后，云端立刻把该账号标记为脚本下线，**之后任何轮询都返回**
  `{"offline": true, "reason": "script_offline"}`，**不会生成任何话术**，不会写库。
- 重启脚本必须带 `"online": true`（或 `action=start`）才能恢复。**不带就一直是下线状态。**
- 即使忘了调 stop 也不会乱发：云端没有定时任务，**脚本不调就没人触发**。

---

## 绝不能做

1. **不要重试同一条**。某条发失败就丢掉，等下一轮；云端已把该会话标记为"这轮补过了"，不会重复给。
2. **不要自己生成或润色文案**。文案由云端按三种形态生成（自说自话 / 给台阶 / 半句钩子），改了就破坏"不掉价"的设计。
3. **不要和主链路混用**。主链路是 `{query, api_key, friend_name}`（每次消耗账号配额）；followup 不消耗配额，两者不要拼在一个请求里。
4. **不要再用 `mode=wake`**。22h 唤醒已下线，现在只会返回 `{"retired": true}`。

---

## 失败处理

| 情况 | 处理 |
|---|---|
| HTTP 非 200 / 超时 | 本轮跳过，60–90 秒后再试。**不要立即重试** |
| `401 invalid_api_key` | API Key 失效，停止轮询并提示用户去「我的简介」重新生成 |
| `{"error":"followup_candidates_failed"}` | 云端缺少 SQL 迁移，停止轮询并报告 |
| `offline: true` | 脚本处于下线状态，补一次 `"online": true` 后恢复轮询 |

---

## 判定规则（云端已做，脚本不用判断）

这些全部在服务端算好，脚本拿到什么发什么：

- 你上一条消息发出去 **5 分钟**没人回，且没超过 **60 分钟**
- 关系阶段是 **吸引 / 舒适 / 恋爱**（"陌生"不补）
- 北京时间 **09:00–23:00**
- **每个会话每天最多补 3 次**，每次沉默期只补 1 条（她回了才重新计时）
- 单轮最多返回 **3 条**（等得久的优先）

---

## 一个必须保证的前提

**她的回复必须落库成 `user` 消息**（你们现有主链路调用已经做了这件事）。

如果收消息那段逻辑没有走主链路落库，云端会一直认为"她没回"，会一路补到每会话 3 次上限。这是最容易踩的坑，务必确认。
