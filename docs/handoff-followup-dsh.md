# 军师 · 追加发话（followup）接入交接 v242

> 给手机端脚本维护方（DSH）。这份文档自包含，按它改即可，不需要看别的资料。
> **协议已从"一次轮询直接拿文案"改为"两阶段"**，旧实现必须改，否则不生效。

## 一句话

轮询只拿"该补发给谁"，**打开那个人的聊天页之后**再回来要文案，拿到就发。没走到打开聊天页那一步，云端一分钱不花、也不记一次补发。

## 为什么改（上一版的实际结果）

上一版是"轮询 → 云端直接生成一段话 → 脚本去发"。结果线上：**云端生成了 18 条，微信里 0 条**。
脚本没发出去，但云端已经落库并记成"补过了"，于是 token 白花、那 3 个好友当天 3 次额度全被占掉、直连上下文里还多了 18 句"我根本没说过的话"。

现在把"生成"推迟到"聊天页确实打开"之后，并加了失败撤回。

## 接口

```
POST https://opzvvgixlfbfpdlsorbi.supabase.co/functions/v1/ima-proxy
Content-Type: application/json
```

### 调用一览

| # | 场景 | 请求体 |
|---|---|---|
| 1 | 脚本启动（必调一次） | `{"mode":"followup","api_key":"<KEY>","online":true}` |
| 2 | 轮询（每 60–90 秒） | `{"mode":"followup","api_key":"<KEY>"}` |
| 3 | 该好友聊天页**已打开** | `{"mode":"followup","api_key":"<KEY>","session_id":"<目标 session_id>"}` |
| 4 | 发送失败 / 没有发出去 | `{"mode":"followup","api_key":"<KEY>","session_id":"<同上>","action":"fail"}` |
| 5 | 脚本退出 / 暂停 | `{"mode":"followup","api_key":"<KEY>","action":"stop"}` |

`"action":"start"` 与 `"online":true` 等价。

---

## 阶段一：轮询（调用 2）

返回**目标列表**，没有文案、不消耗任何模型额度：

```json
{
  "phase": "scan",
  "targets": [
    { "session_id": "9f2c…", "friend_name": "小美", "note": "", "search_key": "小美",
      "waited_min": 7, "used_today": 0 }
  ],
  "followup": [],
  "skipped": [],
  "window": "09:00-23:00",
  "session_cap": 3,
  "online": true
}
```

- `targets` 为空 = 这轮没事，**正常**，不要报错。
- 一次最多 3 个，等得最久的排前面。

**定位微信会话的顺序（重要）**：先 `note`（微信备注，若为空则跳过）→ 再 `search_key` → 最后 `friend_name`。
`search_key` 是云端把昵称里的 emoji、颜文字、空格剥掉后的纯文本（例如 `Iclyn ❄️` → `Iclyn`、`ღ᭄余生🍒安好💖` → `余生安好`），**直接拿整串带 emoji 的昵称去搜多半搜不到**，这正是上一版发不出去的高概率原因之一。

## 阶段二：聊天页打开后要文案（调用 3）

```json
{
  "phase": "generate",
  "followup": [
    { "session_id": "9f2c…", "friend_name": "小美", "note": "", "search_key": "小美",
      "text": "锅贴煎糊了一面 凑合吃吧", "shape": "自说自话",
      "waited_min": 7, "used_today": 1 }
  ],
  "skipped": [],
  "online": true
}
```

- `text` 是最终话术：**原样发出，不改写、不加标点、不加称呼、不补表情**。
- `followup` 空 + `skipped:[{"reason":"target_not_eligible"}]` = 期间她回了 / 已超 60 分钟 / 今日额度用完 → **放弃这条，不要发任何东西**。
- 同一条不要调两次：第一次生成后云端已记成"补过"，第二次会直接返回 `target_not_eligible`。

**顺序必须是：先打开她的聊天页，再调 3，再发。**
云端只在这时候才生成，所以"打不开聊天页"＝不生成＝不花钱。

### 可选：把屏幕上看到的最新聊天内容一起传上来

```json
{ "mode":"followup", "api_key":"<KEY>", "session_id":"<id>",
  "screen_context": "她 20:31 回：今天加班到九点" }
```

云端会把它当可信事实用（≤600 字），补出来的话更接得上。不传也能用。

## 阶段三：发送失败要撤回（调用 4）

发出异常（发送按钮没点中、会话发错了、App 被切走）时立刻调调用 4：

```json
// 返回
{ "rolled_back": true, "followup": [], "targets": [] }
```

云端会删掉刚生成那条（只删 15 分钟内、该会话的最后一条补发），**不计入当日 3 次**，下一轮还能重来。

不调的话这条就算"补过了"，等于白白浪费一次额度——上一版的 18 条就是这么废掉的。

---

## 停止语义

- 调过 `action=stop` 后，云端立刻标记脚本下线，**之后所有调用都返回**
  `{"offline": true, "reason": "script_offline"}`，不生成、不写库（连调用 3 也会被拒）。
- 重启脚本必须带 `"online": true`（或 `action=start`）。**不带就一直是下线状态。**
- 忘了调 stop 也不会乱发：云端没有定时任务，脚本不调就没人触发。

---

## 绝不能做

1. **不要拿阶段一的 `targets` 去发消息**——那里没有文案。
2. **不要自己生成或润色文案**。三种形态（自说自话 / 给台阶 / 半句钩子）由云端按"今天已补次数"轮换，改写会破坏"不掉价"的设计。
3. **不要重试同一条**。发失败就走调用 4 撤回，等下一轮重新生成；直接重发同一条会撞 `target_not_eligible`。
4. **不要和主链路混用**。主链路是 `{query, api_key, friend_name}`，消耗账号配额；followup 不消耗，两者别拼在一个请求里。
5. **不要再用 `mode=wake`**。22h 唤醒已下线，只会返回 `{"retired": true}`。

---

## 失败处理

| 情况 | 处理 |
|---|---|
| HTTP 非 200 / 超时 | 本轮跳过，60–90 秒后再试，**不要立即重试** |
| `401 invalid_api_key` | Key 失效，停止轮询，提示用户去「我的简介」重新生成 |
| `{"error":"followup_targets_failed"}` | 云端缺 SQL 迁移（035），停止轮询并报告 |
| `{"offline":true}` | 补一次 `"online":true` 后恢复 |
| `target_not_eligible` | 正常现象，丢掉这条，继续下一轮 |

---

## 判定规则（云端已做，脚本不用判断）

- 你上一条消息发出去 **≥5 分钟**没人回，且**不超过 60 分钟**
- 关系阶段是 **吸引 / 舒适 / 恋爱**（"陌生"不补）
- 北京时间 **09:00–23:00**
- **每个会话每天最多补 3 次**，每次沉默期只补 1 条（她回了才重新计时）
- 单轮最多 3 个目标（等得久的优先）

## 一个必须保证的前提

**她的回复必须落库成 `user` 消息**（现有主链路调用已经在做）。
如果收消息那段没走主链路落库，云端会一直认为"她没回"，会一路补到每会话 3 次上限。这是最容易踩的坑，务必确认。

## 自测清单（改完按顺序打勾）

1. 轮询返回 `phase:"scan"` 且 `followup` 为空 → 说明没在轮询阶段烧 token
2. 打开某个好友聊天页后调调用 3，拿到 `text`
3. 故意不点发送，调调用 4 → 返回 `rolled_back:true`，云端当日次数不增
4. 正常发一次 → 微信里能看到这句话，直连上下文里也能看到（说明落库成功）
5. 调 `action=stop` → 再轮询得到 `offline:true`
